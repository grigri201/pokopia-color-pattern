# Story 2.1: 基于偏好词和可染色状态筛选推荐候选

Status: done

## Story

As a 用户,
I want 推荐 item 先匹配 Pokemon 偏好词并区分可染色状态,
so that 推荐结果不是随机物品或单纯颜色接近。

## Acceptance Criteria

1. Given Pokemon metadata 包含偏好词，compact item 数据包含名称、分类、tags 和可染色状态, when 推荐候选筛选运行, then 只有命中至少一个 Pokemon 偏好词的 item 可以进入候选, and 未命中偏好词的 item 被排除并可在调试输出中追踪原因。
2. Given 一个 item 命中偏好词且 `isDyeable` 为 true, when 推荐候选筛选运行, then 该 item 可以进入候选, and 不要求 item 主色与 Pokemon 主色和谐。
3. Given 一个 item 命中偏好词且 `isDyeable` 为 false, when 推荐候选筛选运行, then 该 item 被标记为需要 OKLCH 和谐判断, and 不在本故事中绕过该后续判断。

## Dev Notes

- 推荐规则不是“颜色越接近越好”。所有推荐候选必须先命中 Pokemon 偏好词。
- 可染色 item 命中偏好词后不要求主色和谐；不可染色 item 必须继续接受 OKLCH 和谐判断，不能在本故事中直接放行到最终推荐。
- `src/main.ts` 当前有 `furnitureScore()` 以色调关键词和 seeded score 做 runtime 排序；该逻辑不能作为新推荐引擎的依据，后续应被 generated recommendation data 取代。
- `docs/pokopia_image_sources/decorative_item_images.csv` 不是完整 item 数据源；推荐候选应基于 Epic 1 compact item data。
- fixture tests 应使用小样本，不依赖完整 1,219 item manifest 才能表达分支规则。

### Project Structure Notes

- 预期路径：`src/domain/recommendation.ts`、`tests/unit/recommendation.test.ts`、`tests/fixtures/recommendations.fixture.json`。
- 推荐 domain 逻辑应保持 pure，便于 Node 生成脚本、fixture tests 和浏览器展示复用。
- 不要在浏览器中扫描 raw CSV 或重新实现候选筛选。
